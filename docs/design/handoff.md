# 交接（handoff）

Thread 的交接原语：把「一个会话的结论」交给「下一个会话或下一个 Agent」，让接手方开局就带着前序状态，而不是从头摸索。

Thread 只做**状态与交接**，不做调度、不启动会话、不重试。它是编排器的状态底座，不是编排器。

## 什么时候用

- 多角色流水线（分析 → 开发 → 测试），需要把分析结论、已定决策、未决问题、产物指针交下去；
- 人离开电脑后由另一个 Agent 接手同一任务；
- 长任务分段：上一段收尾时明确「下一步做什么」，下一段不该重新判断。

## 四种入口，同一张表

| 入口 | 谁触发 | 场景 |
|---|---|---|
| 收尾事件 | 会话结束（自动） | 主路径：会话一结束就生成 close-out 交接 |
| `/thread-handoff [target]` | 人 | 手动补一条，或指定目标角色 |
| `propose_handoff` 工具 | 模型 | 会话中判断「该同步过去了」 |
| `handoff_next` / `handoff_ack` | 编排器 | 领取与确认（MCP 工具） |

四种入口写同一张 `handoffs` 表、走同一状态机：`pending → delivered → ack`。

## 编排器接入（两步）

```js
// 1) 启动 worker 时多给两个环境变量
env: { THREAD_TASK_ID: taskId, THREAD_ROLE: "dev" }

// 2) 需要时领取交接（MCP 工具，返回结构化 brief）
const next = await mcp.callTool({ name: "handoff_next", arguments: { task_id: taskId, role: "dev" } });
// → { id, status, brief: { goal, decisions[], open[], next[], artifacts[], conditions[], acceptance? } }

await mcp.callTool({ name: "handoff_ack", arguments: { id: next.id } });
```

没有编排器也能用：不传 `task_id`/`role` 时按项目寻址，人开下一个会话，首轮自动注入摘要。

## 契约保证

- **原子领取**：`handoff_next` 是单条 `UPDATE … RETURNING`，「选中最旧 pending」与「推进为 delivered」一步完成——两个 worker 并发不会拿到同一条；
- **幂等**：同一会话重复生成/提议同一目标的交接只保留一条；`handoff_ack` 重复确认仍成功；
- **不阻塞主路径**：交接相关失败一律 fail-open，不影响对话；
- **作用域隔离**：按项目键过滤，跨项目不会串；
- **只放指针与摘要**：`artifacts` 存文件路径，正文留在文档——Thread 是索引与契约层，文档是产物层；
- **带验收状态**：项目登记过验收条目时，brief 多一行 `acceptance`（如 `验收 1/2 已证（缺：lint）`）；会话关闭前会**自动重跑**已登记条目，所以接手方看到的是刚测出的结论，而非上一轮的旧判断。

## 实测价值（2026-11-13，三臂对照）

同一任务、同一份记忆，接手方是一个只收到两句提问的 agent：

| 指标 | 推送交接 | 有记忆、不推送 | 无 Thread |
|---|---|---|---|
| 召回已定方案 | **5/5** | 5/5 | 1/5 |
| 采用生产者策展的下一步 | **5/5** | **0/5** | 0/5 |
| 接手后查询次数 | **1.0** | 6.8 | 4.2 |
| 平均耗时 | **7s** | 15s | 12s |

读法：

- **召回**是记忆层的价值（推送组与自取组都 5/5，无 Thread 组答不出）；
- **策展的下一步**是交接独有的价值——记忆里只有「旧计划」，只有交接带着生产者刚做出的决断（5/5 vs 0/5）；
- **成本**上，推送组几乎不用查（1.0 次 / 7s），自取组要反复查（6.8 次 / 15s）。

方法：每组 5 次独立运行，临时 `THREAD_ROOT` + 空工作区（避免模型读项目文件），以结构化库里的 `handoffs.status` 与工具调用事件计数为证。
